## 3. 영역별 요약

### 3-1. 계좌·이체와 동시성 (C-017, C-020, C-022, C-025)

**무엇이 어떻게 동작하나**
- 입출금·예금·적금 3종. 계좌번호는 종류별 앞자리(110 / 120 / 220)로 발급해 테이블 간 중복 검사를 없애고, 같은 테이블의 충돌은 unique 제약 + 최대 5회 재시도(C-006).
- 이체 `POST /transfers`: 소유자·받는 계좌·자기 계좌 여부를 먼저 거르고(바뀌지 않는 정보) → 두 입출금 계좌를 **ID 오름차순으로 한 번에 `FOR UPDATE`** → 잠근 **뒤에** 잔액·1회 한도·1일 한도 검사 → 양쪽 잔액·거래내역 저장. 1일 한도는 KST 00:00부터, `TRANSFER_OUT`만 센다(C-009, C-022).
- 적금 납입 `POST /transfers/savings`는 입출금 → 적금 순으로 잠그고 잔액만 본다(이체 한도는 적용 안 함).
- 개발용 충전 API `POST /dev/accounts/checking/{id}/charge`로 잔액을 채운다. `ENABLE_DEV_ENDPOINTS`가 켜진 때만 열리고 기본은 꺼짐(C-021, C-050).

**왜 그렇게 정했나**
- READ COMMITTED에서는 두 요청이 같은 잔액을 읽고 둘 다 통과한다(이중 출금, 1일 한도 우회). 대조군 실험에서 잠금을 빼면 10건이 모두 성공했다.
- A→B, B→A 동시 이체는 순서 없이 잠그면 데드락(대조군: 20건 중 18건 실패). 항상 ID 순서로 잠그면 순환이 없다.
- pytest는 SQLite를 유지(편의성 우선)하기로 했고, 대신 PostgreSQL 스크립트로 잠금을 따로 확인한다(C-017 결정, C-025).

### 3-2. 카드·청구서 (C-010 ~ C-013, C-023, C-044)

**무엇이 어떻게 동작하나**
- 신용카드(`4000-`)와 체크카드(`5000-`). 신용 한도는 상품 값을 발급 때 복사(요청으로 받지 않음).
- 체크 결제: 입출금 계좌 → 카드 순으로 잠금, 잔액 출금, 입출금 거래내역(`CARD_PAYMENT`) + 카드 사용내역. 신용 결제: 카드 잠금, `미결제액 + 금액 > 한도`면 거절, **돈은 나가지 않고** 미결제액만 증가.
- 청구서는 스케줄러 없이 **본인이 API로** 생성(`지난달분`, 이용 기간이 끝난 달만)하고 납부한다. 납부는 카드의 결제 계좌에서만 출금. 잠금 순서는 결제 계좌 → 카드 → 청구서, 잠근 뒤 `PAID` 확인.
- 카드 정지·해제·해지(C-044). 신용카드 해지는 미결제액이 0일 때만.

**왜 그렇게 정했나**
- 청구서 생성 때 카드를 잠가야 같은 달 청구서가 동시에 두 번 만들어지지 않는다. 납부 버튼 중복 클릭은 "잠근 뒤 PAID 확인"으로 막는다.
- 자동 출금·연체·리볼빙은 범위 밖(C-010, 3-3은 ⬜).

### 3-3. 예금·적금 (C-033, C-034, C-043, C-076, C-079, C-080)

**무엇이 어떻게 동작하나**
- **예금**: 개설 요청에 `initial_amount`·`from_checking_account_id`·출금 계좌 비밀번호가 필수. 개설·약관 동의 기록·입금이 **한 트랜잭션**이라 0원 예금이나 "개설만 되고 입금 실패"가 생기지 않는다. 가입 후 추가 입금은 없다. 상품별 최소 가입 금액(`min_amount`, `BELOW_MIN_AMOUNT`).
- **적금**: 자유 금액·여러 번 납입(`monthly_payment`는 안내용, C-034).
- 만기일부터 입금 거절(`ACCOUNT_MATURED`), 해지된 계좌 입금 거절(`ACCOUNT_CLOSED`).
- **해지**(`POST /accounts/{deposit|savings}/{id}/close`): 입금 건별 단리 일할 이자(원 미만 버림), **만기 후에는 이자가 늘지 않음**, 만기 전 해지는 금리의 50%. 원금+이자를 내 입출금 계좌로 보내고 계좌는 `status=CLOSED`로 남긴다(거래내역 보존).

**왜 그렇게 정했나**
- 예금은 사용자 결정으로 "실제 정기예금처럼 가입 때 금액을 정한다"(C-079). 개설·이체를 나누면 반쪽 상태가 남는다.
- 상태는 **잠근 뒤에** 확인한다(해지 ↔ 해지, 해지 ↔ 납입 동시 요청에서 닫힌 계좌에 돈이 갇히지 않게).
- 이자는 **해지 시점의 상품 금리**로 계산한다. 개설 당시 금리는 저장하지 않는다(C-043 한계).

### 3-4. 인증·세션·쿠키·기기 등록 (C-083 ~ C-088, C-096, [AUTH.md](AUTH.md))

**무엇이 어떻게 동작하나**
- 로그인 → 액세스 토큰(5분 JWT, `sid` 클레임) + 갱신 토큰(30분 슬라이딩). 갱신 토큰은 256비트 임의값이고 DB에는 SHA-256만 저장. 쓸 때마다 **회전**하고, 이미 교체된 토큰이 다시 오면 탈취로 보고 세션 전체 폐기(`REFRESH_TOKEN_REUSED`).
- **요청마다 세션 확인**(C-087): 액세스 토큰의 `sid` 세션이 살아 있는지 DB로 본다. 로그아웃·비밀번호 변경·재사용 감지가 즉시 적용된다.
- **단일 세션**(C-088): 다른 곳에서 로그인하면 기존 세션 종료(`SESSION_REPLACED`). 세션을 바꾸는 모든 작업은 **users 행 → refresh_tokens** 순서로 잠근다.
- **쿠키 전환**(C-096): 갱신 토큰은 `httpOnly; Secure; SameSite=Strict; Path=/api/users` 쿠키(JSON 본문에 없음), 액세스 토큰은 프론트 메모리에만. `refresh`·`logout`은 쿠키만 읽고 **`Origin` 필수**(없거나 목록 밖이면 403 `CSRF_ORIGIN`). 프론트는 Next.js `rewrites`로 `/api/*`를 FastAPI에 프록시해 쿠키가 first-party가 된다(서버 환경변수 `API_ORIGIN`).
- **기기 등록**(C-096): 새 기기 로그인 = 비밀번호 → `DEVICE_VERIFICATION_REQUIRED` 챌린지 → 휴대폰 인증 → `POST /users/login/device`. 통과하면 1년짜리 `device_token` 쿠키(서버엔 SHA-256)가 생긴다. 실패 카운터는 **등록 기기 채널 / 새 기기 채널을 따로** 센다. 비밀번호 재설정·탈퇴는 기기를 전부 해제, 비밀번호 변경은 유지.
- 입력 정규화(C-084): 아이디는 공백 제거 + 소문자(가입 규칙 `^[a-z0-9_]{4,20}$`, 로그인은 형식 검사 없음), 비밀번호는 영문·숫자·특수문자 필수. 422 메시지는 서버에서 한국어 문장으로(C-085).

**왜 그렇게 정했나**
- `localStorage` 토큰은 XSS로 읽혀 밖으로 나간다. 읽을 수 없는 토큰은 훔칠 수 없다. **한계:** 페이지가 열려 있는 동안의 XSS는 사용자인 척 API를 부를 수 있다. 그래서 돈이 나가는 곳의 계좌 비밀번호·휴대폰 인증이 계속 중요하다.
- CSRF는 `SameSite=Strict` + 쿠키 경로 + `Origin` 검사의 세 겹이다. Strict는 브라우저가 지키는 약속, Origin은 서버가 직접 하는 검사라 한쪽이 뚫려도 남는다.
- 액세스 토큰을 순수 JWT(무상태)로 두면 로그아웃 뒤에도 최대 5분 유효해서 "은행에서는 위험"하다는 사용자 판단으로 C-087에서 바꿨다. 이 프로젝트는 원래 요청마다 사용자를 읽어서 추가 비용은 인덱스 조회 1번.
- 기기 등록으로 "아이디만 알면 5번 틀려 주인을 잠글 수 있는" 문제를 줄인다(공격자는 새 기기 채널만 잠글 수 있음).

### 3-4b. 타행 이체: ClearingHub (C-105, [INTERBANK.md](INTERBANK.md), 규격은 루트 `SPEC.md`)

**무엇이 어떻게 동작하나**
- 새 도메인 `domains/interbank/`. **보내기**: 계좌 비밀번호 확인 → 한 트랜잭션으로 출금 + `interbank_transfers(PENDING)` → 허브 `POST /v1/transfers` → 결과 반영. **받기**: 허브가 부르는 `/interbank/inquiry|receive|receive/{id}`에서 Ed25519 서명을 입금 전에 검증하고, `transfer_id`(기본키)로 같은 ID는 한 번만 입금하며, 응답에도 서명을 붙인다.
- 결과를 모르는 거래(타임아웃·5xx·서명이 틀린 응답)는 PENDING으로 두고 백그라운드 작업(`worker.py`)이 30초마다 허브에 확인한다. 환불은 허브가 확정 실패(`FAILED`)라고 답했을 때만 한다.
- 설정은 `.env`의 `HUB_URL`, `HUB_PUBLIC_KEY`, `BANK_CODE`, `BANK_NAME`, `BANK_API_KEY`, `BANK_PRIVATE_KEY`(값은 문서에 적지 않는다). 하나라도 비면 타행 이체만 꺼진다(`503 INTERBANK_DISABLED`). 은행 이름은 SpiderBank, 코드 903.
- 이체 화면(C-107)은 4단계이고 최근·자주 쓰는·내 계좌 탭이 있다. 거래내역의 상대 이름은 사람 이름·가맹점만 쓴다(은행 이름 없음, C-108). 홈 카드의 '최근 이체한 분'도 같은 서버 목록(`/transfers/recent`)을 쓰며 타행 상대를 누르면 은행 코드까지 실어 금액 화면으로 간다(C-111). 대부분의 화면은 떠났다 돌아오면 처음부터 시작하지만 이체의 미확정 요청은 결과 확인을 위해 보존한다(C-109, C-112).

**왜 그렇게 정했나**
- 허브가 입금을 끝냈는데 응답만 늦은 경우 출금을 되돌리면 이중 지급이 된다. 그래서 "모르는 상태"는 되돌리지 않고 확인한다.
- 같은 ID가 동시에 오면 4xx를 주지 않고 200/503만 쓴다(4xx면 허브가 "입금 안 됨"으로 처리해 보낸 은행이 환불하기 때문).
- **AI 비서에는 일부러 연결하지 않았다**(SPEC 6절: 허브 호출은 이체 서비스 안에서만).
- **한계:** 정산·대사(SPEC 10절)·본인 계좌 조회(9절) 미구현, 실제 허브와의 902·셀프 시험 전체는 안 함, 확인 작업 간격 고정 30초(C-105 논의 포인트). C-112부터 PENDING 타행 이체가 있으면 탈퇴를 막는다.

### 3-5. 계정 복구·잠금·계좌 비밀번호 (C-090 ~ C-094, 조사 내용은 C-090 ~ C-093)

**무엇이 어떻게 동작하나**
- **은행식 로그인 잠금**(C-090): 같은 아이디로 5회 연속 틀리면 `ACCOUNT_LOCKED`(403). 검증 **전에** `UPDATE ... failed_login_count + 1 ... RETURNING`을 자기 트랜잭션으로 커밋한다. 동시 요청이 5번을 가져가 검증 중이면 429(잠김이 아님). 이전의 메모리 한도(C-040, C-082, C-089)는 이것으로 대체됐고 IP 한도(15분 20회)만 메모리에 남는다.
- **휴대폰 인증**(C-091): 6자리, 10분, 5회, 1회성, 저장은 HMAC-SHA256. 같은 번호 15분 3번(DB, PG advisory lock), IP 15분 10번. 실제 문자 업체는 없고 로컬 개발 환경에서만 **개발용 문자함**(`GET /dev/sms`)을 쓴다. 운영의 시연 계정 새 기기 인증은 C-115를 따른다.
- **계좌 비밀번호**(C-092): 숫자 4자리(동일·연속 금지), 5번 틀리면 계좌 잠금. 체크카드 결제는 제외.
- **복구**(C-093): `POST /recovery/start`는 정보가 맞든 틀리든 **항상 같은 200**(같은 문구·모양·비슷한 응답 시간). 가짜 복구 토큰도 진짜와 구별되지 않는다. 비밀번호 재설정 성공 시 잠금 해제·모든 세션 폐기·알림 문자, 자동 로그인 없음. 계좌 없이 두 비밀번호를 모두 잊으면 온라인 복구 불가, 관리자 명령(`uv run python -m avengers_bank.admin unlock|reset-password <login_id>`).

**왜 그렇게 정했나**
- 조사 결과 국내 은행은 계좌 + 휴대폰 두 요소로 복구하고, 전자금융감독규정은 5회 이내 오류 시 거래 중지 + 본인 확인 후 재부여를 요구한다(C-090). 복구 절차가 생겨서 "잠금 공격"의 피해가 줄었다.
- 6자리 코드는 경우의 수가 100만이라 그냥 해시하면 DB 유출 시 역산된다 → HMAC.
- 응답 동일화는 계정·계좌 존재 여부 노출을 막는다(OWASP).

### 3-6. 회원 탈퇴 (C-095)

**무엇이 어떻게 동작하나**
- 조건: 예금·적금 해지, 입출금 잔액 0, 신용카드 미결제와 PENDING 타행 이체 없음(`GET /users/me/withdrawal`의 `blockers`). `POST`는 현재 비밀번호 + 휴대폰 인증(`WITHDRAWAL`)이 필요하고, 계좌를 잠근 뒤 PENDING 이체를 다시 확인한다(C-112).
- **소프트 삭제**: 이름 "탈퇴회원"으로 가림, 전화·닉네임 제거, 비밀번호 해시 무효화, **`login_id`는 유지해 재가입을 막는다**. 입출금 계좌 `closed_at`, 카드 전부 `CLOSED`, 세션·AI 대화·인증 행 삭제. 계좌·거래내역·청구서·약관 동의 기록은 **보존**.
- 탈퇴 후 로그인은 없는 아이디와 같은 401, 남이 그 계좌로 이체하면 없는 계좌와 같은 404.

**왜 그렇게 정했나**
- 탈퇴가 "잔액 0"을 확인한 직후 남의 입금이 들어오면 돈이 남은 탈퇴 계좌가 생긴다. 탈퇴와 이체가 같은 입출금 계좌 행을 잠그고, 이체는 잠근 뒤 `require_open`으로 닫힘을 확인한다. PG 검증에서 "탈퇴했는데 돈이 남음" 0건, 잠금 뺀 대조군은 20번 모두 발생.

### 3-7. 약관·RAG·AI 금융 비서 (C-070 ~ C-075, C-081, C-099 ~ C-103, [AGENT.md](AGENT.md), [TERMS_RAG.md](TERMS_RAG.md))

**무엇이 어떻게 동작하나**
- **AI 비서**(`POST /agent/chat`): 모델이 Tool(계좌 목록·자산 요약·거래내역·카드 결제 현황·이체 초안·약관 검색·약관 조항)을 골라 부른다. 이체는 `prepare_transfer`가 5분짜리 **초안만** 만들고, 사용자가 화면에서 확인(`/agent/transfers/{id}/confirm`, 계좌 비밀번호 필요)해야 실행된다. 공급자는 `model_client.py` 한 파일에 격리(Gemini `gemini-2.5-flash`, `GEMINI_API_KEY` 없으면 `/agent/chat`만 503).
- **AI 비서의 최근 변화**(C-099 ~ C-103): 모델↔도구 반복을 **LangGraph**(`graph.py`)로 옮겼다(동작 동일, checkpointer 없음, 대화는 `agent_messages`에만). 이체 Tool은 계좌를 id가 아니라 **이름**으로 받고 서버가 찾는다(없음·여럿이면 후보를 돌려 되묻기). 이체 한도 오류에는 한도 금액을 담아 모델이 한도를 지어내지 않게 했다. 새 Tool `prepare_open_account`는 예·적금 **가입 준비 카드**만 만들고 가입은 하지 않는다(약관 동의·계좌 비밀번호는 가입 화면에서 직접, 만기 날짜는 서버가 계산).
- **약관 동의**: `docs/terms`를 발행 명령이 검증해 불변 버전으로 저장(`terms_versions`). 가입 시 서버가 본 집합(`revision_id`·`set_hash`)과 요청을 대조한다(`TERMS_OUTDATED`, `TERMS_INVALID`, `TERMS_REQUIRED_NOT_AGREED`, 약관 없는 상품은 `TERMS_NOT_CONFIGURED`). 가입은 상품 행 `FOR SHARE`, 발행은 `FOR UPDATE`.
- **약관 검색(RAG)**: 조항 단위 청크 + Gemini 임베딩(768) + pgvector + bigram 보정, 임계값 0.6. 범위(상품·버전)는 서버가 먼저 정한다. 출처(`[[src:버전:조항]]`)는 모델이 아닌 **서버가 이번 검색 결과로만** 만든다(없는 링크 방지).
- 예금 약관 4개는 C-081에서 1.1.0으로 개정·발행했다(나머지는 1.0.0).

**왜 그렇게 정했나**
- 가입 때 "무엇에 동의했는지" 나중에 증명하려면 서버가 버전을 보존해야 한다. 화면 체크박스만으로는 API 직접 호출을 못 막는다.
- 이체 초안 확인은 조건부 UPDATE(PENDING → EXECUTED)라 확인 버튼 중복 클릭에도 한 번만 이체된다(PG 대조군 10건 성공).
- **운영 주의:** 약관은 **새 버전 → publish → indexing**을 해야 RAG가 채워진다. 안 하면 가입이 409이거나 검색이 `TERMS_INDEX_NOT_READY`로 빈다(절차는 TERMS_RAG.md). 본문은 발행 후 덮어쓸 수 없고 새 버전으로 올려야 한다.

### 3-8. 프론트엔드 (C-055 ~ C-069, C-072 ~ C-074, C-077, C-086, C-094, C-106 ~ C-113, C-116)

- Next.js 16(App Router) + React 19 + TypeScript + Tailwind 4, 클라이언트 컴포넌트만 사용. API 호출은 `frontend/lib/api.ts` 한 곳(서버 `{data}`/`{error}` 모양 해석, 401 → 갱신 → 재시도, single-flight + Web Locks).
- 하단 탭(홈·이체·상품·내 정보), 피치 디자인·Pretendard·반응형(C-057, C-058), 홈은 모바일 뱅킹 앱 형태(C-065 ~ C-068), 금융상품 화면(C-069), 카드 상세·청구서 납부(C-062, C-063), 거래 검색(C-064).
- 세션 타이머("자동 로그아웃 29:41"), 만료 예고, 자동 갱신(C-086). 휴대폰 인증·계좌 비밀번호·찾기·해지 화면(C-094). 우하단 AI 비서 패널(C-070, 폭 조절 C-073), 예·적금 가입 준비 카드(C-103), 계좌 상세 정리·이자 미리 보기(C-104), 이체 4단계 화면·최근/자주 쓰는 계좌(C-107), 거래내역 이름 통일(C-108), 화면 상태 초기화(`useFreshOnLeave`, C-109: 같은 탭에서 다음 사용자에게 지난 입력·완료 화면이 보이지 않게).
- **접속**: 운영은 서버 주소 한 곳에서 화면과 API를 모두 낸다(C-110). 로컬 개발은 브라우저를 `http://localhost:5173`으로만 연다(프록시·쿠키 때문). `NEXT_PUBLIC_API_BASE_URL`은 없고 서버 환경변수 `API_ORIGIN`을 쓴다(C-096). 로컬 프론트로 **서버** API를 쓰려면 `API_ORIGIN=https://<서버 주소>/api`(끝에 `/api`, C-110부터).
- **운영 빌드(`npm run build`)**: 예전에는 `/find-id` 등 프리렌더 검사에서 실패했다. 렌더링 중 `Date.now()`·`new Date()`·`useParams`를 쓰는 화면이 많아서이고, `app/layout.tsx`에서 `{children}` 전체를 `Suspense`로 감싸 해결했다(C-110). 새 화면을 만들면 로컬에서 `npm run build`로 먼저 확인한다.
- **화면 상태**: Next.js `cacheComponents`는 화면을 떠나도 지우지 않고 숨겨 상태를 보존한다. 대부분의 화면 본체는 `useFreshOnLeave()`의 key로 다음 방문을 처음부터 시작하게 했다(C-109). 이체는 예외로, C-112부터 미확정 요청 ID와 이체 의도를 저장해 돌아왔을 때 결과를 확인한다. 계좌 비밀번호는 저장하지 않는다. 계좌 상세의 거래내역 필터는 방문마다 초기화된다.
- **모든 화면 폭 통일**: `components/ui.tsx`의 `Shell`이 한 폭(`max-w-xl`)으로 가운데에 놓는다(C-107 후속).

### 3-9. 배포 (C-052 ~ C-056, [DEPLOY.md](DEPLOY.md))

- Docker 이미지(워커 1개) + Caddy(자동 HTTPS) + 외부 DB(RDS). API 포트는 내부 네트워크에만(`X-Forwarded-For` 조작으로 IP 한도를 우회하지 못하게). AWS 시드니 리전, 도메인 없이 sslip.io(C-054).
- **두 번째 배포(2026-11-10)**: 서버가 오래된 커밋에 있어 마이그레이션 10개가 한꺼번에 적용됐다(표·컬럼 추가뿐). 배포 전 RDS 스냅샷을 찍었다. 운영 DB 데이터도 따로 맞췄다: 상품 시드 → 약관 발행 → 약관 색인(순서가 중요, [DEPLOY.md](DEPLOY.md)).
- **프론트 배포(C-110)**: `web` 컨테이너(Next.js standalone) + Caddy 주소 나누기. `/interbank/*`(허브가 부르는 타행 이체)·`/health`·`/docs`는 API로 바로, `/api/*`는 `/api`를 떼고 API로, 나머지는 화면으로 간다. 옛 직접 API 주소(`https://서버/transfers/...`)는 닫혔다. `.env.prod`의 `CORS_ORIGINS`에 서버 주소가 있어야 로그인 유지가 된다.
- **서버에 접속할 때 막히면**: 거의 항상 EC2 보안 그룹 22번 규칙의 "내 IP"가 바뀐 것이다(장소·와이파이를 바꾸면 발생, 이 기간에 여러 번 겪었다). 콘솔에서 22번 규칙을 내 IP로 다시 저장한다.
- **운영의 한계**: 실제 SMS 발송 업체가 아직 없어 일반 계정의 새 기기 로그인·가입·비밀번호 재설정 인증번호는 문자로 전달되지 않는다. `/dev/sms`도 운영에서는 닫혀 있다. 지정된 시연 계정의 새 기기 로그인에만 기간 제한 코드를 적용했다(C-115); 가입·복구 인증에는 적용되지 않는다. 개발용 충전 API도 닫혀 있다.
- 서버 주소(`sslip.io`)는 EC2 IP에 묶여 있다. IP가 바뀌면 주소·허브 `base_url`(`PATCH /v1/me`)·`CORS_ORIGINS`를 모두 바꿔야 한다.

### 3-10. 2026-11-10 안정화·알림·시연 인증 (C-112 ~ C-115)

- **휴대폰 변경**: 일반 프로필 수정으로 번호를 바꿀 수 없다. 전용 API에서 현재 비밀번호, 기존 번호와 새 번호에 각각 묶인 1회성 인증을 검증한 뒤 모든 세션·등록 기기를 폐기한다(C-112).
- **이체 재시도**: 새 화면은 일반·타행 이체에 UUID `request_id`를 보낸다. 같은 내용의 같은 ID는 기존 결과를 돌려주고 내용이 달라지면 409다. 일반 이체 결과는 `GET /transfers/requests/{request_id}`, 타행 결과는 `GET /interbank-transfers/{transfer_id}`로 본인 확인 후 조회한다. 이전 API에서 저장된 미확정 의도는 새 API에 다시 보내지 않는다(C-112, C-114).
- **입출금 알림**: 신규 거래내역과 알림을 한 트랜잭션에 저장한다. 알림함에는 상대방·금액·계좌·거래 후 잔액과 읽음 상태가 남는다. 접속 중에는 5초 간격 조회로 화면 팝업을 띄우며 브라우저 알림은 권한 허용 시에만 뜬다. 앱을 닫았을 때는 알림함에 보관되고 팝업은 뜨지 않는다. 이전 거래는 소급 알림을 만들지 않는다(C-113).
- **시연용 새 기기 인증**: 서버 `.env.prod`의 계정·등록 번호·코드·만료 시각 네 값이 모두 맞을 때만, 비밀번호 챌린지 이후 `NEW_DEVICE` 인증에 적용된다. 현재 설정은 `2026-11-12T00:00:00+09:00` 만료이며 시연 후 네 값을 제거해야 한다. 코드 원문은 문서에 쓰지 않는다(C-115).
- **배포·미확정 거래**: API·웹을 같은 소스로 배포했고 운영 DB head는 `e4f5a6b7c8d9`다. 기존 10,000원 타행 이체는 출금 내역 1건, 환불 0건, `PENDING`이며 허브 조회 결과가 `UNKNOWN`이다. 허브에서 완료 또는 실패가 확정될 때까지 같은 거래를 재송금하거나 수동 환불하지 않는다(C-114).

## 4. 지켜야 할 코드 규칙

1. **먼저 잠그고, 잠근 뒤에 검사한다**(ERD 규칙 9, C-017). 잠그기 전에 읽은 잔액·상태·`PAID`·`ACTIVE`로 판단하면 동시 요청이 모두 통과한다. 소유자·존재 여부처럼 바뀌지 않는 정보만 잠금 전에 확인한다.
2. **잠금 순서를 고정한다.** 입출금 계좌(ID 오름차순) → 예금·적금 → 카드 → 청구서. 사용자 세션 작업은 users 행 → refresh_tokens(·user_devices). 탈퇴는 users → 입출금 계좌 → 예금·적금 → 카드. 순서가 다르면 데드락이다.
3. **잠금 쿼리에 `populate_existing=True`.** 세션에 남은 예전 값이 최신 값 대신 쓰이지 않게 한다.
4. **롤백되는 카운터 함정.** 실패 횟수(로그인·계좌 비밀번호·인증번호·복구)는 본 작업과 같은 트랜잭션에 두면 실패로 롤백될 때 함께 사라져 무한 대입이 가능하다. **검증 전에 별도 트랜잭션으로 먼저 증가·커밋**한다(C-090, C-091, C-092). 재사용 감지 폐기를 커밋해야 할 때도 트랜잭션 안에서 예외를 던지지 말고 블록 밖에서 401을 낸다(C-083).
5. **상태 변경은 잠근 뒤 확인 + 조건부 UPDATE.** 1회성(인증번호 소비, AI 이체 초안 확인)은 `WHERE consumed_at IS NULL` / `status='PENDING'` 같은 조건 UPDATE 한 문장으로 보장한다.
6. **`db.begin()` 안에서 오래 걸리는 일을 하지 않는다.** 잠금이 풀리지 않는다. argon2 해시는 트랜잭션 전에 만든다(C-045).
7. **`get_current_user`는 일부러 별도 세션을 연다**(C-018). `get_db`를 같이 쓰면 이후 `async with db.begin()`이 "이미 시작됨" 오류를 낸다. 고치지 말 것.
8. **돈이 닫힌 계좌로 가지 않게**: 입출금 계좌에 쓰는 모든 경로(이체·납입·해지금·체크 결제·청구서 납부·충전)가 잠근 뒤 `require_open`을 거친다(C-095).
9. **존재 여부를 흘리지 않는다.** 남의 계좌·카드 404 통일(C-031), 없는 아이디도 가짜 해시로 검증(C-026), 복구 응답 동일화(C-093), 탈퇴 계좌는 없는 계좌와 같은 응답(C-095). 새 오류 경로를 만들 때 이 원칙을 깨지 않는지 본다.
10. **돈을 바꾸는 코드를 고치면 PG 스크립트를 다시 돌린다.** pytest(SQLite)는 `FOR UPDATE`를 무시해서 잠금 버그를 못 잡는다. 새 동시성 검증에는 **잠금을 뺀 대조군**을 같이 만들어 검증이 문제를 알아보는지 확인하는 것이 이 프로젝트의 관례다.
11. **DB 구조를 바꾸면 마이그레이션을 새로 만들고**(파일명 `날짜_시각-리비전_설명.py`), 모델 변경 후 `scripts/generate_erd_drawio.py`로 ERD v2를 다시 만든다. 원본 drawio(v1)는 고치지 않는다.
12. **`core/`·`main.py`는 공용 파일**(PROJECT_STRUCTURE.md는 수정 전 팀 공유를 요구). 건드렸으면 DESIGN_CHANGES 1부 끝의 목록에 적는다.
13. **변경하면 문서도 같이**: DESIGN_CHANGES 4부 항목 + 1~3부·부록 B + NEXT_STEPS 상태(작성 규칙은 DESIGN_CHANGES 맨 아래).

### 5-2. 알려진 한계·후속 과제

- **프로세스 메모리 상태**(서버가 여러 대면 공유 저장소 필요): IP 한도(로그인 20회, 인증번호 10회), 가짜 복구 토큰의 시도 횟수. 워커 1개가 전제(C-052).

- **AI 비서**: 도구 입력 오류 메시지가 영어(C-085), 모델 답변의 자동 평가 없음(검색 평가만 자동, hit@3 24/24), 상품명 없는 질문에서 검색을 건너뛸 수 있음(C-081), 가입 상품 후보를 안 보여 주고 되묻는 경우(C-103), 오래된 대화·초안 정리 정책 없음, 임계값 0.6 여유가 작음(C-075).
- **금융 기능**: 가입 당시 금리 미보존(C-043, C-075), 이체 취소 없음(3-2), 납부일 자동 출금·연체(3-3), 체크카드 1일 한도(3-5), 상품 등록 관리자 API(3-6), 운영용 외부 입금(3-8)은 모두 ⬜. 신규 이체에는 요청 ID가 있으나 기존 이체 기록을 모두 연결한 것은 아니다(C-112). 수수료·예약 이체는 하지 않기로 함(C-046).
- **운영**: 로그·감사 기록(4-2), 계좌·카드 목록 페이징(4-5), CI(4-11)는 ⬜.
- **알려진 허점(알고 감수)**: 신용카드 발급 장수 제한 없음(C-013), 이체의 받는 계좌번호 존재 여부가 드러남(C-038), 회원가입 409로 아이디 존재가 드러남(C-039), 탈퇴와 같은 순간 새 계좌 개설은 못 막음(C-095).

## 7. 직접 확인하는 법

명령과 환경 준비(Docker·`.env`·서버 실행·테스트·PG 스크립트 실행법, Windows 주의, 낡은 서버 확인, 개발용 문자함)는 이 문서 **8장 개발 환경 메모**와 `scripts/README.md`에 있다. 여기서는 무엇을 확인할지만 적는다.

1. **상태**: `git status`로 변경 파일을 확인하고, 연결 대상 DB에서 `uv run alembic current`가 `e4f5a6b7c8d9`(head)인지 확인한다. 로컬 개발 DB와 운영 DB는 별개다.
2. **전체 테스트**: C-114 배포 전 독립 SQLite DB에서 `499 passed, 5 skipped`였다. C-115 뒤에는 관련 기기 인증 21건, 일반 인증·복구 42건이 통과했고 전체 모음은 재실행하지 않았다. SQLite는 행 잠금을 검증하지 못한다.
3. **동시성(PostgreSQL)**: `scripts/pg_*_concurrency.py` 12개. 돈·잠금·세션 코드를 고쳤다면 다시 돌린다. 각 스크립트는 잠금을 뺀 대조군으로 "검증이 문제를 알아보는지"도 보여 준다. 이체·카드·충전·해지, 예금 가입, 토큰 갱신, 단일 세션, 로그인 잠금, 계좌 비밀번호, 기기 채널, 탈퇴, AI 이체 확인을 각각 다룬다(대응 표는 `scripts/README.md`).
4. **브라우저**(`http://localhost:5173`로 접속): 로그인 후 콘솔 `document.cookie`에 `refresh_token`이 **보이지 않아야** 한다. 새로고침해도 로그인이 유지돼야 하고, `localStorage`에는 `session_expires_at`만 있어야 한다(AUTH.md 11장).
5. **Swagger**: `http://127.0.0.1:8000/docs`. 새 기기 로그인의 인증번호는 개발 모드에서 서버 로그 또는 `GET /dev/sms?phone=...`로 본다(`ENABLE_DEV_ENDPOINTS=true` 필요).
6. **문서와 코드 대조**: 이 문서의 수치(테스트 개수, head)가 낡았는지는 위 1~2번으로 다시 확인한다.

## 8. 개발 환경 메모

(예전 `HANDOFF.md`의 개발 환경 부분을 옮겨 현재 기준으로 고쳤다.)

- **실행**: 백엔드 `uv run fastapi dev`(127.0.0.1:8000, Windows라 `fastapi run` 금지), 프론트 `cd frontend && npm run dev`(5173), DB `docker compose up -d --wait`. PC를 다시 켜면 Docker Desktop과 DB 컨테이너를 먼저 올린다. 프론트는 `/api`로 프록시하므로 브라우저는 `http://localhost:5173`으로만 접속한다(Swagger는 `:8000/docs` 그대로).
- **서버 API를 로컬 프론트로 쓰기**: `cd frontend && API_ORIGIN=https://<서버 주소>/api npm run dev -- -p 5173`(끝에 `/api`, 포트 5173 고정: 서버 CORS가 `localhost:5173`을 허용). 로컬 API를 볼 때는 `API_ORIGIN=http://127.0.0.1:8000`.
- **낡은 서버 주의**: 예전에 띄운 `fastapi dev`가 8000번에 남아 있으면 새 코드가 안 올라간다. 이상하면 `Get-NetTCPConnection -LocalPort 8000,5173 -State Listen`으로 확인하고 내린다. 개발 서버는 `.next`를 쓰므로 `npm run build`를 돌릴 때는 개발 서버를 잠깐 멈춘다.
- **테스트**: PowerShell에서 `$env:PYTHONIOENCODING='utf-8'; $env:TEST_DATABASE_URL='sqlite+aiosqlite:///./test_main.db'; uv run pytest -q -p no:cacheprovider`(전체는 약 16~30분). 다른 테스트 실행과 DB 파일을 공유하지 않도록 실행마다 별도 파일명을 쓰고, 종료 후 해당 파일을 정리한다. 로그인 테스트는 `BankClient`가 새 기기 챌린지를 실제 경로로 자동 인증한다. 타행 이체 테스트는 허브를 `httpx.MockTransport`로 흉내 내서 설정 없이 돈다(예시 키는 규격 2.3의 공개 값).
- **PG 동시성 스크립트**: `uv run python scripts/pg_*_concurrency.py`(목록은 `scripts/README.md`). 개발 DB를 쓰지만 `verify_…` 사용자만 만들고 지운다.
- **인증번호**: 개발 모드의 `GET /dev/sms?phone=…`(화면의 "개발용 문자함")은 `ENABLE_DEV_ENDPOINTS=true`일 때만 열린다. 운영에서는 닫혀 있고 실제 SMS 발송도 아직 없다. 시연 계정의 새 기기 로그인에만 기간 제한 서버 설정을 쓴다(C-115). 다른 계정·가입·복구에는 적용되지 않는다.
- **관리자 명령**: `uv run python -m avengers_bank.admin unlock|reset-password <login_id>`(두 채널 잠금 해제, reset-password는 기기도 전부 해제).
- **로그인 실패 시험**: 실행 중인 서버 앞에서 반복하면 같은 IP(127.0.0.1)가 IP 한도(15분 20회)에 걸린다. 실패 시험은 테스트(ASGI)나 PG 스크립트로 한다.
- **타행 이체를 로컬에서 시험**하려면 `.env`에 허브 설정(`.env.example` 참고)을 채운다. 없으면 그 기능만 꺼진다. 실제 허브 등록·키 관리는 [INTERBANK.md](INTERBANK.md).
- **시험 데이터**: 기존 계좌(예: `admin123`)는 계좌 비밀번호가 없어 이체 전에 계좌 상세에서 휴대폰 인증 후 설정해야 한다. `seed_demo.py`는 로그인을 먼저 시도하므로 기존 아이디엔 본인 비밀번호를 인자로 넣어 실행한다(틀리면 로그인 실패로 셈). 로컬 DB에 시험 계정이 여럿 있다(로그인 정보는 문서에 적지 않는다; 필요하면 `admin reset-password`).
- **`frontend/AGENTS.md`**: 이 Next.js는 버전이 달라 새 API는 `node_modules/next/dist/docs/`를 먼저 확인한다.
- **PowerShell 주의**: 인라인 한글 출력은 `PYTHONIOENCODING=utf-8`이 없으면 깨진다. 터미널 출력이 깨져 보이는 것은 대개 인코딩 문제다.

## 9. 사용자와 일하는 방식 (AI 세션용)

- **한국어로 대화**. 큰 작업은 먼저 설계·선택지를 제안하고 사용자가 정한 뒤 시작한다(바로 만들지 말 것). 보안·정책은 필요하면 먼저 조사한다.
- 정한 뒤에는 **서브에이전트로 병렬 작업**한다: 파일 소유권을 나눠 주고, 커밋·DB 적용·배포는 메인이 한다. 백엔드·프론트·문서처럼 서로 막히지 않는 일은 동시에 돌려 시간을 줄인다. 에이전트 보고는 그대로 믿지 말고 결과를 직접 확인한다.
- 바뀐 것은 `docs/DESIGN_CHANGES.md`에 C-번호 항목(변경 전/후·이유·영향·검증·논의 포인트)과 개요 표, `NEXT_STEPS.md`를 갱신한다. 인증은 학습용으로 `docs/AUTH.md`에 "무엇을 왜 바꿨는지"를 설명한다.
- **커밋·푸시·서버 배포는 사용자가 말했을 때만** 한다. 서버·운영 DB를 바꾸는 일(시드, 약관 발행, 시험 계정·가짜 잔액)은 범위를 먼저 확인받는다. 키·초대 코드·비밀번호는 채팅과 문서에 적지 않고 `.env` 계열 파일에만 둔다(`.env.*`는 git에서 제외돼 있다).
- 운영 서버에 시험 계정으로 로그인해 보는 확인은 하지 않는다(사용자가 직접 한다).
