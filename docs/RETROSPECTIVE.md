# 회고록 (작성 중)

AvengersBank을 만들고 배포하면서 **무엇을 왜 선택했는지**를 모아 두는 문서다. 지금은 기록해 둘 것을 먼저 쌓는 단계이고, 글로 다듬는 건 나중에 한다.
변경의 이유와 검증은 [DESIGN_CHANGES.md](DESIGN_CHANGES.md)에 더 자세히 있다. 여기에는 **판단과 배운 점** 위주로 적는다.

> 이어 쓰는 방법: 새 결정이 생기면 "기술 선택 기록"에 항목을 추가한다. 배운 점·아쉬운 점은 각 항목의 "배운 점"에 적고, 나중에 모아서 아래 "정리할 것"으로 옮긴다.

## 기술 선택 기록

### 1. 리버스 프록시: nginx 대신 Caddy (2026-11-05, 배포 준비, C-052)

**상황.** AWS에 올리려면 FastAPI 앞에서 HTTPS를 받아 줄 프록시가 필요하다. 선택지는 nginx(+certbot), Caddy, 그리고 AWS ALB(+ACM 인증서)였다.

**고른 것.** Caddy. 같은 서버(EC2) 안에서 Docker Compose로 API와 함께 띄운다.

**이유.**
- **HTTPS 인증서가 자동이다.** Caddyfile에 도메인만 적으면 Let's Encrypt에서 인증서를 받고 만료 전에 갱신한다. nginx는 인증서를 받는 `certbot`을 따로 설치하고 자동 갱신(cron/timer)까지 직접 설정해야 하고, 갱신을 놓치면 어느 날 HTTPS가 만료된다.
- **설정이 짧다.** 우리가 쓴 설정 파일은 4줄이다(`deploy/Caddyfile`). 같은 일을 하는 nginx 설정은 `server` 블록 2개(443, 80 리다이렉트), 인증서 경로, 프록시 헤더까지 길어진다.
- **ALB를 쓰지 않아도 된다.** AWS 무료티어에서는 ALB가 요금과 도메인 설정 부담이 크다. Caddy로 EC2 한 대에서 HTTPS를 끝내면 그 비용이 없다.
- **이 규모에서는 성능 차이가 의미 없다.** 시연용 API 한 개라 nginx의 성능 이점이 필요하지 않다.

**포기한 것(nginx의 장점).** 사용 사례와 자료가 훨씬 많고 실무에서 흔히 만난다. 문제가 생겼을 때 검색해서 찾을 답이 Caddy보다 많다. 나중에 실무 경험이 목적이 되면 nginx로 다시 해 볼 만하다.

**함께 알게 된 것.**
- Caddy는 CA(인증서 발급 기관)가 아니다. 인증서는 Let's Encrypt가 발급하고, Caddy는 그걸 **대신 받아 주고 갱신하는 서버 프로그램**이다.
- Let's Encrypt는 도메인 소유를 확인하므로 **도메인이 있어야** 일반적으로 발급된다. IP 주소만으로는 안 된다.
- 프록시 뒤에서는 접속자 IP가 프록시 주소로 보인다. 로그인 실패 제한(C-040)이 IP별로 세므로 uvicorn에 `--proxy-headers`를 줘서 `X-Forwarded-For`의 실제 IP를 읽게 했다. 이걸 안 하면 한 명이 틀려도 모두가 잠긴다.

**확인한 것.** 컨테이너를 로컬에서 띄워 `X-Forwarded-For: 203.0.113.9`를 보내 보니 서버 로그에 그 IP가 찍혔다. Caddyfile은 `caddy validate`로 문법을 확인했다.
**확인하지 못한 것.** 실제 도메인에서의 인증서 발급은 아직 해 보지 못했다(도메인·서버가 아직 없다).

**배운 점.** 도구를 고를 때 "더 유명한 것"과 "지금 상황에 필요한 것"을 구분해야 한다. 이번에는 인증서 갱신을 잊는 사고를 막고 설정량을 줄이는 게 우선이어서 덜 유명한 쪽을 골랐다.

### 2. AWS 구성: EC2 한 대 + RDS, 도메인 대신 sslip.io (2026-11-06, 첫 배포, C-053·C-054)

**상황.** 시연용 API 하나를 크레딧을 아끼면서 HTTPS로 올려야 했다. 도메인은 없었다.

**고른 것.**
- **EC2(t3.micro) 한 대에 API와 Caddy를 Docker Compose로 띄움.** ECS·Fargate·ALB는 쓰지 않았다.
- **DB는 RDS PostgreSQL 17(db.t4g.micro), EC2에서만 접근.** 같은 EC2에 DB 컨테이너를 두는 방법도 있었다.
- **도메인은 sslip.io**(`<IP의 점을 하이픈으로>.sslip.io`). 처음엔 HTTP로만 하려 했다(C-053).

**이유.**
- **EC2 한 대:** 워커 1개짜리 API라 오토스케일링이나 로드밸런서가 필요 없다. Fargate·ALB·NAT Gateway는 켜 두기만 해도 요금이 나간다.
- **RDS:** 백업과 패치가 자동이고, EC2가 망가져도 데이터가 남는다. 버전은 로컬 개발 DB와 같은 17로 맞췄다. 테스트와 동시성 검증을 17에서 했기 때문이다.
- **sslip.io:** 처음엔 "도메인이 없으면 HTTP"라고 생각했다. 그런데 IP를 담은 이름을 그 IP로 돌려주는 공개 DNS가 있으면 도메인 없이도 Let's Encrypt 인증서를 받을 수 있다. HTTP였다면 비밀번호와 JWT가 평문으로 오가고, 나중에 HTTPS 프론트에서 API를 부를 때 브라우저가 막는다(혼합 콘텐츠).

**포기한 것.** 서울 리전(시드니에 만들어졌다), 고정된 예쁜 주소(IP가 바뀌면 주소도 바뀐다. 탄력적 IP로 막았다), RDS 다중 AZ(장애 대비).

**함께 알게 된 것.**
- **RDS "빠른 구성으로 생성"은 Aurora 서버리스로 고정이다.** 프리 티어가 아니라서 지우고 다시 만들었다. 콘솔이 권하는 기본 버튼이 가장 싼 선택은 아니다.
- **t3 인스턴스의 크레딧 기본값은 "무제한"**이라 CPU를 오래 쓰면 추가 요금이 나올 수 있다. "표준"으로 바꿨다.
- **CORS는 API 주소가 아니라 API를 부르는 프론트 주소를 넣는 설정이다.** 주소창에 API를 직접 치거나 서버끼리 호출할 때는 CORS와 상관없다.
- **Compose는 기본으로 `.env`만 읽는다.** `--env-file .env.prod`를 빼먹으면 변수가 비어 멈춘다. 비어 있으면 안내하고 멈추게(`${DOMAIN:?...}`) 해 둔 덕에 원인을 바로 알았다.

**확인한 것.** HTTPS로 `/docs` 접속, 회원가입(RDS 저장), 로그인, 내 정보 수정.
**확인하지 못한 것.** 계좌·카드·이체를 배포 환경에서 차례로 실행해 보는 것, 서버 재부팅 후 자동 복구.

**배운 점.** "할 수 없다"고 정한 것(도메인 없이는 HTTPS 불가)도 한 번 더 찾아보면 싼 방법이 있다. 반대로 콘솔의 "빠른" 버튼처럼 편해 보이는 선택은 비용을 확인하고 눌러야 한다.

### 3. 프론트엔드: Vite + React 대신 Next.js (2026-11-06, C-055)

**상황.** API만 있고 화면이 없어서, 시연할 때 Swagger로만 보여 줄 수 있었다. React를 쓰기로 하고 그 위에 무엇을 얹을지 골라야 했다.

**고른 것.** Next.js(App Router) + TypeScript + Tailwind CSS. 같은 저장소의 `frontend/` 폴더에 둔다.

**비교한 것.**
| | Vite + React | Next.js |
|---|---|---|
| 정체 | 빌드 도구 + UI 라이브러리 | React 위의 프레임워크 (라우팅·서버 기능 포함) |
| 페이지 주소 | `react-router`를 따로 설치 | 폴더 구조가 곧 주소 (`app/transfer/page.tsx` → `/transfer`) |
| 서버 기능 | 없음 | 있음. 하지만 FastAPI가 서버라서 쓸 일이 거의 없음 |
| 배울 양 | 적음 | 더 많음 (서버 컴포넌트와 클라이언트 컴포넌트 구분) |

**이유.** 국내 채용 공고에 Next.js가 자주 나와서, 배우는 김에 이력서에 쓸 수 있는 쪽을 골랐다. 기능을 다 쓸 필요는 없어서 모든 화면을 `"use client"`로 만들고, 브라우저에서 FastAPI를 부르는 순수 React처럼 썼다.

**포기한 것.** Vite의 단순함. 이 규모라면 Vite가 더 가볍고, "API 호출 → 화면 표시" 흐름도 더 그대로 보인다.

**함께 알게 된 것.**
- **CORS는 포트 하나로 해결했다.** 백엔드의 CORS 기본값이 `localhost:5173`이라 Next 개발 서버를 `-p 5173`으로 띄웠다. 백엔드 코드를 고치는 것보다 작은 변경이다.
- **로그인 상태를 어디에 둘지가 보안 문제다.** 간단히 `localStorage`에 토큰을 넣었지만, 페이지에 악성 스크립트가 들어오면(XSS) 토큰을 읽어 갈 수 있다. 실서비스는 httpOnly 쿠키를 쓴다.
- **브라우저는 `localhost`와 `127.0.0.1`을 다른 주소로 본다.** CORS 비교도, 일부 환경의 접속 가능 여부도 다르다.
- Next.js 16에서는 effect 안에서 바로 `setState`를 부르면 lint가 오류로 막는다. 마운트 뒤 `localStorage`를 확인하는 경우처럼 정당한 곳에만 이유를 적고 예외로 뒀다.

**확인한 것.** 로컬에서 가입 → 계좌 개설 → 충전 → 이체 → 잔액 부족 오류까지 브라우저로 확인했다.
**확인하지 못한 것.** Vercel 배포, 배포된 API와의 연결.

**배운 점.** 기술을 고를 때 "이 프로젝트에 필요한 것"과 "내가 배우고 싶은 것"이 다를 수 있다. 다르다면 무엇을 포기했는지 알고 고르면 된다.

### 4. AI 금융 비서: Gemini + 직접 돌리는 Tool Calling 루프 (2026-11-06, C-070·C-071)

**상황.** 은행 기능을 AI가 쓰게 하는 것이 프로젝트 목표다(나중에 MCP). 그 전에 일반 Tool Calling으로 채팅 비서를 만들었다. 저장소에는 AI 공급자 설정이 없었다.

**고른 것.**
- 공급자: Google Gemini, 공식 Python SDK(`google-genai`). 기본 모델 `gemini-2.5-flash`.
  - 처음에는 Anthropic Claude(`claude-opus-5-5`)로 만들었다가, 사용자가 Gemini API를 쓰기로 정해서 바꿨다(C-071). 공급자 코드를 `model_client.py` 한 파일에 가둬 둔 덕분에 Tool·서비스·테스트·화면은 그대로 두고 그 파일과 설정만 바꿨다.
- 루프: SDK의 자동 Tool Runner 대신 `service.py`에서 직접 돌린다.

**이유.**
- **직접 돌리는 루프:** 모델 호출 횟수·Tool 개수 상한, Tool 결과에서 이체 action을 꺼내는 일, 가짜 클라이언트로 테스트하기를 우리 코드가 쥐고 있어야 했다. 공급자 코드는 `model_client.py` 한 파일에 가두고, 서비스는 중립 타입만 쓴다.
- **Tool은 공급자를 모르는 함수:** `(db, 로그인 사용자, pydantic 인자) → pydantic 결과`. 나중에 MCP가 같은 함수를 부르면 된다.
- **이체는 초안까지만:** 모델이 실수하거나 속아도 돈이 나가지 않도록, 실행은 사용자가 누르는 확인 API로만 한다.
- **Flash 모델:** 채팅은 응답 속도와 비용이 중요하고, 계산은 백엔드가 하므로 큰 모델이 필요한 일이 적다.

**포기한 것.** 공급자 독립 라이브러리(LiteLLM 등)를 쓰면 공급자를 설정만으로 바꿀 수 있지만, 의존성이 늘고 공급자별 기능(생각 서명 보존, 자동 함수 실행 끄기)을 세밀하게 다루기 어렵다. 우리는 인터페이스만 나눠 두고 필요할 때 구현을 하나 더 쓰기로 했다.

**함께 알게 된 것.**
- **이중 이체 막기:** 확인 버튼을 동시에 여러 번 눌러도 한 번만 이체되도록, "PENDING일 때만 EXECUTED로 바꾸는" 조건부 UPDATE를 이체와 같은 트랜잭션에 넣었다. 이체가 실패하면 상태도 함께 되돌아간다. PostgreSQL 스크립트에서 대조군(조건 없이 덮어쓰기)은 10번 모두 이체됐다.
- **모델을 믿지 않는다:** Tool 인자는 pydantic(`extra="forbid"`)으로 다시 검증해서 `user_id` 같은 인자는 거절한다. 사용자는 항상 JWT에서 온다.
- **합계는 코드가 한다:** 모델은 덧셈·뺄셈을 틀릴 수 있어서 부족 금액·남은 일수까지 Tool이 계산해 준다.

**확인한 것.** `tests/test_agent.py`(가짜 모델 클라이언트, 18개), `scripts/pg_agent_confirm_concurrency.py`(PostgreSQL 동시 확인).
**확인하지 못한 것.** 실제 Gemini API로 대화한 결과(키 없이 작업). 답변 품질은 키를 넣고 직접 확인해야 한다.

**배운 점.** AI에게 맡기는 범위를 "조회와 초안"으로 좁히고, 돈이 움직이는 마지막 단계는 사람의 확인 + 기존 검증 코드에 두면, 모델이 틀려도 피해가 작다.

### 약관 동의와 약관 검색 RAG (C-075, 2026-11-07)

**정한 것.**
- 약관은 Markdown이 작성 원본, DB가 발행된 불변 스냅샷. 동의는 "어느 버전 집합(revision)을 봤는지"까지 서버가 검증·기록한다.
- 벡터 저장소는 따로 두지 않고 이미 쓰는 PostgreSQL에 pgvector. 문서가 작아(청크 123개) 근사 인덱스 없이 정확 검색.
- 임베딩은 `gemini-embedding-001`(768차원). 채팅과 같은 공급자·같은 키, 클라이언트는 `EmbeddingClient` 인터페이스로 분리.
- 출처는 모델이 만들지 않는다. 모델은 서버가 준 ID를 표시만 하고, 서버가 그 요청에서 실제로 검색된 것만 출처로 만든다.

**이유.**
- **pgvector:** DB 하나로 원문·동의·벡터를 같이 다루면 "그 버전의 그 조항"을 조인 하나로 거른다. 별도 벡터 DB는 운영할 것이 하나 늘어난다. 로컬 이미지는 C-048에서 뺐던 pgvector 이미지로 되돌렸다(같은 PG 빌드라 볼륨 그대로).
- **버전 집합 비교 + 행 잠금:** 체크박스만으로는 "열어 둔 화면의 약관이 그 사이 바뀐" 경우를 못 막는다. 가입은 상품 행 공유 잠금, 발행은 배타 잠금으로 서로 기다리게 했다.
- **필터 먼저, 검색은 나중:** 상품·버전을 서버가 먼저 정하면 다른 상품 조건이 섞일 수 없다. 모델은 질문과 상품만 고른다.

**포기한 것.** LangChain 같은 RAG 프레임워크(이 정도 크기엔 추상화가 더 크다), 근사 벡터 인덱스(HNSW, 문서가 작다), 형태소 분석 키워드 검색(글자 bigram으로 충분했다), 모델 답변의 자동 평가(호출 비용, 지금은 검색 평가만 자동).

**함께 알게 된 것.**
- 실제 모델로 돌려 보니 가짜 클라이언트 테스트에서 안 보이던 문제가 나왔다: 상품 이름을 말해도 ID를 몰라 되묻기, 할인 질문에 검색 없이 답하기, 같은 대화 뒤쪽에서 검색 건너뛰기. 앞의 둘은 서버 쪽 상품 이름 해석과 프롬프트로 고쳤다.
- 임계값은 감으로 정할 수 없었다. 0.5에서는 근거 없는 질문도 "관련 있음"이 됐고(무관한 조항도 0.56~0.6), 실측 스윕으로 0.6을 골랐다. 여유가 작아서 평가 질문을 더 늘려야 한다.
- 역할 분담: 문서·평가 질문은 Codex, 코드는 Claude. `docs/terms/README.md`에 형식 계약을 먼저 적어 둔 덕분에 문서가 오기 전에 fixture로 코드를 만들고, 문서가 오자 바로 검증·평가할 수 있었다.

**확인한 것.** pytest 226개(실제 PostgreSQL 잠금·pgvector 포함), 실제 임베딩 검색 평가 27문항(`docs/TERMS_EVAL.md`), 임시 DB에서 발행→색인→동의 가입→실제 Gemini 채팅.
**확인하지 못한 것.** 브라우저에서 화면을 직접 눌러 보기, 같은 대화 안 반복 질문에서 검색을 건너뛰지 않는지, 운영 DB 확장 활성화.
