## 기술 선택 기록

### 1. 리버스 프록시: nginx 대신 Caddy (2026-11-05, 배포 준비, C-052)

**상황.** AWS에 올리려면 FastAPI 앞에서 HTTPS를 받아 줄 프록시가 필요하다. 선택지는 nginx(+certbot), Caddy, 그리고 AWS ALB(+ACM 인증서)였다.

**고른 것.** Caddy. 같은 서버(EC2) 안에서 Docker Compose로 API와 함께 띄운다.

**이유.**
- **HTTPS 인증서가 자동이다.** Caddyfile에 도메인만 적으면 Let's Encrypt에서 인증서를 받고 만료 전에 갱신한다. nginx는 인증서를 받는 `certbot`을 따로 설치하고 자동 갱신(cron/timer)까지 직접 설정해야 하고, 갱신을 놓치면 어느 날 HTTPS가 만료된다.
- **설정이 짧다.** 우리가 쓴 설정 파일은 4줄이다(`deploy/Caddyfile`). 같은 일을 하는 nginx 설정은 `server` 블록 2개(443, 80 리다이렉트), 인증서 경로, 프록시 헤더까지 길어진다.
- **ALB를 쓰지 않아도 된다.** AWS 무료티어에서는 ALB가 요금과 도메인 설정 부담이 크다. Caddy로 EC2 한 대에서 HTTPS를 끝내면 그 비용이 없다.
- **이 규모에서는 성능 차이가 의미 없다.** 시연용 API 한 개라 nginx의 성능 이점이 필요하지 않다.

**포기한 것(nginx의 장점).** 사용 사례와 자료가 훨씬 많고 실무에서 흔히 만난다. 문제가 생겼을 때 검색해서 찾을 답이 Caddy보다 많다. 나중에 실무 경험이 목적이 되면 nginx로 다시 해 볼 만하다.

**함께 알게 된 것.**
- Caddy는 CA(인증서 발급 기관)가 아니다. 인증서는 Let's Encrypt가 발급하고, Caddy는 그걸 **대신 받아 주고 갱신하는 서버 프로그램**이다.
- Let's Encrypt는 도메인 소유를 확인하므로 **도메인이 있어야** 일반적으로 발급된다. IP 주소만으로는 안 된다.
- 프록시 뒤에서는 접속자 IP가 프록시 주소로 보인다. 로그인 실패 제한(C-040)이 IP별로 세므로 uvicorn에 `--proxy-headers`를 줘서 `X-Forwarded-For`의 실제 IP를 읽게 했다. 이걸 안 하면 한 명이 틀려도 모두가 잠긴다.

**확인한 것.** 컨테이너를 로컬에서 띄워 `X-Forwarded-For: 203.0.113.9`를 보내 보니 서버 로그에 그 IP가 찍혔다. Caddyfile은 `caddy validate`로 문법을 확인했다.
**확인하지 못한 것.** 실제 도메인에서의 인증서 발급은 아직 해 보지 못했다(도메인·서버가 아직 없다).

**배운 점.** 도구를 고를 때 "더 유명한 것"과 "지금 상황에 필요한 것"을 구분해야 한다. 이번에는 인증서 갱신을 잊는 사고를 막고 설정량을 줄이는 게 우선이어서 덜 유명한 쪽을 골랐다.

## 정리할 것 (회고록에 넣을 후보)

- 설계 변경을 C-001부터 하나씩 기록하며 작업한 방식(`DESIGN_CHANGES.md`)이 새 세션에서도 이어 작업하는 데 어떻게 도움이 됐는지.
- 동시성: pytest(SQLite)는 행 잠금을 검증하지 못해서 PostgreSQL 검증 스크립트를 따로 둔 이유(C-017, C-025)와, 잠금을 뺀 "대조군"으로 검증이 문제를 알아보는지 확인한 방식.
- "잠근 뒤에 확인한다": 해지·입금 같은 동시 요청에서 잠그기 전에 읽은 상태는 낡을 수 있다는 것(C-043, C-044).
- 중간에 놓친 것: C-043 때 `pg_unique_violation_message.py`를 다시 돌리지 않아 한 단계 뒤에야 실패를 발견한 일(C-044). 스키마를 바꾸면 SQL을 직접 쓰는 스크립트도 같이 확인해야 한다.
- 많은 항목을 "나중에"로 둔 판단(학습·시연용이라는 가정)과 그 기준.
- AWS 무료티어에서 피해야 할 것(NAT Gateway, Fargate, ALB, 퍼블릭 IPv4)과 EC2 + RDS 구성으로 정한 이유 (배포를 마치면 결과와 함께 적는다).
