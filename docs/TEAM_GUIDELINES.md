# 팀 기획 가이드라인

은행 앱을 도메인(계좌, 이체, 카드, 입출금, 예적금, 대출 등)으로 나눠 기획하고, Claude·Codex 같은 AI와 함께 만들 때 팀이 공통으로 맞출 것을 정리한 문서입니다.

문제는 대부분 도메인 안이 아니라 **도메인 사이**에서 생깁니다. 그래서 이 문서는 "각자 정해도 되는 것"이 아니라 "반드시 공통으로 맞출 것"만 다룹니다.

이 문서는 일반 원칙입니다. 이 저장소의 현재 코드가 각 항목을 지키는지 점검한 결과가 아닙니다. 실제 금융 규제(전자금융거래법, 개인정보보호법 등)는 다루지 않습니다.

## 먼저 합의할 것

전부를 한 번에 정할 필요는 없습니다. 아래 여섯 가지를 먼저 정하고, 나머지는 충돌이 생길 때 채웁니다.

1. 공통 용어집 (2절)
2. 돈에 관한 공통 규칙 (3절)
3. 본인 소유 확인 규칙 (4절)
4. AI가 사람 승인을 받아야 하는 작업 목록 (5절)
5. AI에 주면 안 되는 정보 등급표 (6절)
6. 도메인 기획서 템플릿 (9절)

---

## 1. 도메인 경계와 소유권

- **데이터 주인은 하나**: 잔액은 계좌 도메인만 바꿉니다. 이체·카드·대출은 계좌에 출금을 요청할 뿐, 잔액을 직접 고치지 않습니다.
- **경계가 애매한 기능은 미리 배정**: 자동이체(이체 vs 계좌), 체크카드 결제(카드 vs 입출금), 대출 상환(대출 vs 이체), 적금 납입(예적금 vs 이체)은 담당을 표로 적어 둡니다.
- **의존 방향**: 계좌가 맨 아래에 있고 나머지가 계좌를 참조합니다. 순환 참조는 금지합니다.
- **여러 도메인이 모이는 화면**(홈 등)은 담당자를 따로 둡니다.

## 2. 공통 용어와 표기

- **용어집**: 같은 단어를 다르게 쓰지 않습니다. 예: 잔액 vs 출금가능금액, 이체 vs 송금, 해지 vs 해약.
- **상태값 이름**: 예: 계좌 `정상/정지/해지`, 거래 `대기/완료/실패/취소`.
- **표기**: 금액·날짜 형식, 버튼 문구("확인"/"다음"/"이체하기")를 통일합니다.
- **공통 화면 요소**: 금액 입력, 계좌 선택, 비밀번호 입력, 확인 모달, 완료 화면은 한 번만 만들어 재사용합니다.

## 3. 돈에 관한 공통 규칙

- **금액 표현**: 원 단위 정수로 다룹니다. 이자 계산의 절사·반올림 규칙은 하나로 정합니다.
- **모든 잔액 변동은 거래 기록을 남김**: 기록 없는 잔액 변경은 없습니다.
- **중복 요청 방지**: 같은 요청이 두 번 와도 한 번만 처리합니다.
- **실패 시 원상복구**: 출금은 됐는데 입금이 실패한 경우의 처리 원칙을 정합니다.
- **한도와 기준 시각**: 1회·1일 한도, 날짜 기준(KST 자정), 점검 시간을 정합니다.

## 4. 보안

### 인증과 권한
- **본인 것만 접근**: 모든 조회·변경에서 대상이 로그인한 사용자의 것인지 서버가 확인합니다. 화면에서 숨기는 것만으로는 부족합니다.
- **행동별 인증 수준 표**: 조회는 로그인, 이체·해지·한도 변경은 계좌 비밀번호 재확인 식으로 한 표에 정합니다.
- **시도 횟수 제한**: 로그인·계좌 비밀번호 오류 횟수와 잠금·해제 방법을 통일합니다.
- **세션**: 만료 시간, 자동 로그아웃, 다른 기기 로그인 처리를 정합니다.

### 데이터 보호
- **비밀번호는 해시로만 저장**: 원문을 저장하거나 로그에 남기지 않습니다.
- **마스킹 규칙**: 계좌번호·카드번호·전화번호를 어디서 얼마나 가릴지 정합니다.
- **로그 금지 항목**: 비밀번호, 카드번호 전체, 토큰은 로그와 오류 메시지에 넣지 않습니다.
- **비밀 값 관리**: API 키와 DB 비밀번호는 환경변수에만 두고 커밋하지 않습니다.

### 입력과 요청
- **서버가 최종 검증**: 금액(음수, 0, 한도 초과), 계좌 상태, 소유자를 서버에서 다시 확인합니다.
- **오류 메시지로 정보 노출 금지**: "없는 계좌"와 "남의 계좌"를 구분해 알려 주지 않습니다.
- **오류 형식 통일**: 잔액 부족, 한도 초과, 횟수 초과는 모든 도메인이 같은 형식을 씁니다.
- **허용 출처와 요청 빈도 제한**을 공통으로 둡니다.

### 기록과 동의
- **감사 기록**: 로그인, 이체, 해지, 한도 변경, 실패한 시도를 남기는 방식을 통일합니다.
- **약관·동의**: 상품 가입 시 동의 기록을 남기는 방식을 통일합니다.
- **알림**: 어떤 사건에 알림을 보낼지와 문구 톤을 정합니다.

## 5. AI 개발 도구(Claude, Codex) 작업 규칙

규칙은 저장소의 규칙 파일에 둡니다. Claude는 `CLAUDE.md`, Codex는 `AGENTS.md`를 읽으므로 한쪽에 내용을 쓰고 다른 쪽은 그 파일을 가리키게 합니다.

### 작업 범위
- **자기 도메인 폴더만 수정**: 다른 도메인이나 공통 코드를 바꿔야 하면 멈추고 사람에게 묻습니다.
- **요청받은 것만**: 시키지 않은 리팩터링, 파일 이동, 이름 변경은 하지 않습니다.
- **기존 것 재사용**: 금액 표시, 비밀번호 입력, 오류 형식은 이미 있는 것을 씁니다.

### 사람 승인이 필요한 작업
- DB 스키마 변경과 마이그레이션
- 의존성 추가
- 인증·권한·잔액 변경 코드 수정
- 배포, 강제 푸시, 데이터 삭제
- 다른 도메인이 쓰는 API의 형식 변경
- 공통 규칙 문서와 테스트 파일의 수정·삭제

### 금지 사항
- 비밀 값(`.env`, 키, 토큰)을 읽어서 출력하거나 커밋하지 않습니다.
- 실제 개인정보를 테스트 데이터로 쓰지 않습니다.
- 테스트를 통과시키려고 테스트를 지우거나 검증을 끄지 않습니다.
- 보안 검사(소유자 확인, 횟수 제한)를 임시로도 우회하지 않습니다.

### 보고
- 끝났다고 보고하기 전에 테스트를 실제로 돌리고, 못 돌렸으면 그렇게 말합니다.
- 추측한 부분(확인 안 한 API, 가정한 규칙)은 명시합니다.
- 문서와 코드가 어긋나면 임의로 한쪽에 맞추지 않고 사람에게 알립니다.

### 협업
- 커밋 메시지 형식, 변경 기록 위치, 브랜치·PR 규칙을 정합니다. 여러 명이 각자 AI를 돌리면 같은 파일을 동시에 고치는 충돌이 가장 흔합니다.

## 6. 앱에 붙이는 AI 에이전트의 가드레일

**원칙: "말하지 말라고 시키는 것"은 가드레일이 아니고, "아예 안 주는 것"이 가드레일입니다.** 차단은 프롬프트가 아니라 AI 앞단의 코드에서 합니다.

### 정보 등급표

| 등급 | 예시 | 처리 |
|---|---|---|
| **절대 금지** | 로그인·계좌 비밀번호, 카드 전체 번호·CVC·유효기간, 인증번호, 세션 토큰, API 키, 주민등록번호 | AI에 전달하는 경로를 만들지 않음 |
| **가려서 전달** | 계좌번호, 카드번호, 전화번호, 이메일, 주소 | 마스킹하거나 별칭으로 바꿔 전달 |
| **필요할 때만** | 잔액, 거래내역, 대출 잔액, 신용 관련 정보 | 질문에 필요한 범위·기간만 전달 |

새 필드를 만들 때 등급을 정하지 않으면 기획이 끝난 것이 아닙니다.

### AI가 받는 것
- **허용 목록 방식**: 넘겨도 되는 필드만 골라 담습니다. 금지 필드를 빼는 방식은 필드가 추가될 때 구멍이 납니다.
- **AI 전용 응답 형식**: 화면용 API 응답을 그대로 AI에 넘기지 않습니다.
- **사용자가 대화창에 입력한 민감정보**: AI에 보내기 전에 패턴으로 가리고, 여기에 입력하지 말라고 안내합니다.
- **비밀번호는 AI를 거치지 않음**: 별도 입력 화면에서 받아 서버로 바로 보냅니다.
- **사용자 식별은 서버 세션에서**: AI가 넘기는 값으로 사용자를 정하지 않습니다.
- **자유 입력 텍스트는 데이터**: 거래 메모, 받는 분 표시명, 계좌 별칭에 섞인 지시문을 명령으로 따르지 않게 합니다.

### AI가 하는 것
- AI는 사용자 본인 권한 안에서만 동작하고, 그 확인은 서버가 합니다.
- 돈이 움직이는 행동은 AI가 준비만 하고 사용자가 화면에서 최종 확인합니다.

### AI가 내놓는 것
- **출력 검사**: 답변에 계좌번호·카드번호가 전체로 나오면 보여 주기 전에 가립니다.
- **시스템 정보 노출 금지**: 프롬프트 내용, 내부 오류 메시지, 테이블 이름, 다른 사용자 존재 여부가 나오지 않게 합니다.
- **오류 문구**: 서버 오류를 그대로 AI에 넘기지 않고 정리된 문구만 넘깁니다.

### 저장과 외부 전송
- **대화 기록**: 저장 여부, 보관 기간, 삭제 방법을 정하고, 저장한다면 가려진 상태로 저장합니다.
- **로그**: AI에 보낸 내용과 받은 내용에도 같은 등급표를 적용합니다.
- **외부 AI 업체**: 대화가 외부 서버로 전송된다는 점을 기획에 명시하고, 학습 사용 여부와 보관 정책을 확인합니다.
- **MCP로 노출할 때**: 외부 에이전트는 통제 밖이므로 화면보다 좁게 줍니다. 도구마다 반환 필드 목록을 기획서에 적습니다.

## 7. 테스트

### AI가 짠 코드의 테스트
- **기대 결과는 사람이 정함**: AI가 코드와 테스트를 같이 쓰면 틀린 동작을 통과시키는 테스트가 나옵니다. 기대 결과는 기획서에서 가져옵니다.
- **기획서의 예외 케이스가 곧 테스트 목록**: 예외 케이스 한 줄에 테스트 하나가 대응합니다.
- **돈·권한 로직은 테스트 필수**: 잔액 변동, 한도, 이자 계산, 소유자 확인, 시도 횟수 제한.
- **도메인 간 약속 테스트**: 도메인이 서로 요청하는 형식을 테스트로 고정합니다.
- **합치기 전 자동 실행**: AI의 보고가 아니라 실행 결과를 믿습니다.

### AI 에이전트 자체의 테스트
AI는 같은 질문에도 답이 달라지므로 문장이 아니라 **행동**을 검사합니다.

- **시나리오 묶음**: 질문과 기대 행동(어떤 도구를 어떤 값으로 불렀는가)을 목록으로 관리합니다.
- **해서는 안 되는 일**: 6절의 가드레일마다 하나씩 둡니다. 비밀번호를 물어도 답하지 않는가, 남의 계좌가 조회되지 않는가, 메모에 심은 지시문을 따르지 않는가, 금지 등급 정보가 AI 입력에 들어가지 않는가.
- **애매한 요청**: 계좌가 여럿이거나 금액이 빠졌을 때 추측하지 않고 되묻는지 확인합니다.
- **여러 번 실행**: 통과율로 봅니다. 돈·보안 시나리오는 100%가 기준입니다.
- **변경 시 재실행**: 프롬프트, 모델, 도구 설명을 바꾸면 전체 시나리오를 다시 돌립니다.
- **실제 실패 사례 추가**: 사용 중 발견한 오동작은 시나리오로 추가합니다.

### 테스트 환경
- 테스트용 데이터만 쓰고, 실제 돈이 움직이지 않는 환경에서 돌립니다.
- 가드레일 검사는 AI 판단에 맡기지 않고 코드로 확인합니다.

## 8. 문서(마크다운) 관리

사람과 AI가 모두 문서를 읽고 움직입니다. 문서가 틀리면 AI는 틀린 문서를 그대로 따릅니다.

- **한 가지 사실은 한 곳에만**: 규칙은 한 파일에 쓰고 다른 문서는 링크로 가리킵니다.
- **문서 종류를 나눔**:

| 종류 | 내용 | 바뀌는 빈도 |
|---|---|---|
| 규칙 | 돈·보안·AI 작업 규칙, 정보 등급표 | 드물게, 합의 후 |
| 기획서 | 도메인별 현재 사양 | 기능이 바뀔 때 |
| 결정 기록 | 무엇을 왜 바꿨는지 | 추가만 함 |
| 할 일 | 다음 작업, 미결 사항 | 수시로 |

- **현재 상태와 변경 이력을 분리**: 기획서에는 지금 맞는 내용만 둡니다. 이력이 섞이면 AI가 옛 규칙을 현재 규칙으로 읽습니다.
- **AI가 읽는 규칙 파일은 짧게**: 항상 적용되는 것만 최상위에 두고, 도메인별 세부는 해당 폴더 문서로 내립니다.
- **확인 가능한 문장으로**: "신중하게 작성" 대신 "잔액 변경 코드는 테스트 없이 커밋 금지".
- **지켜지지 않는 규칙은 고치거나 지움**.
- **문서와 코드는 같은 커밋에**: 사양을 바꾸는 변경에 문서 수정이 없으면 리뷰에서 돌려보냅니다.
- **소유자**: 도메인 기획서는 도메인 담당자, 공통 규칙은 전원 합의로 바꿉니다.
- **색인**: 문서 목록과 한 줄 설명을 한 곳에 둡니다(이 저장소는 `README.md`의 문서 표).
- **주기적 정리**: 해결된 미결 사항과 끝난 할 일을 치우고, 문서가 코드와 맞는지 훑습니다.

## 9. 도메인 기획서 템플릿

모든 도메인이 같은 목차로 씁니다.

1. 목적과 범위 (하지 않는 것 포함)
2. 사용자 시나리오
3. 상태와 전이 (예: 개설 → 정상 → 해지)
4. 규칙·제약 (한도, 수수료, 이자)
5. 예외 케이스 (잔액 부족, 해지된 계좌, 동시 요청) → 테스트 목록이 됨
6. **다른 도메인에 요청하는 것과 제공하는 것**
7. **AI에 제공하는 정보와 제공하지 않는 정보** (필드별 등급)
8. **AI 시나리오**: 할 수 있는 일, 되물어야 하는 경우, 거절해야 하는 경우 각 3~5개
9. 화면 목록
10. 미결 사항

각자 쓴 뒤 6번끼리 맞춰 보면 도메인 사이의 빈틈이 드러납니다.

## 10. 협업 절차

- **결정 기록**: 공통 규칙을 바꾸면 무엇을 왜 바꿨는지 한 곳에 남깁니다.
- **변경 영향 공유**: 다른 도메인에 영향을 주는 변경은 합의 후 반영합니다.
- **기획 순서**: 계좌 → 입출금·이체 → 예적금·카드 → 대출 순으로 의존성을 따릅니다.
- **1차 범위 합의**: 도메인별로 꼭 필요한 것만 먼저 정합니다.
